# TaskFlow workflow

Use the actual assignment as authority. Choose the medium, stack and methods from its requirements and existing environment. This pack supplies coordination, not a domain solution or a new permission grant.

1. Read [the decision policy](references/decision-policy.md). Before action, report and discuss a concrete work batch and obtain explicit approval; reuse existing approval inside its scope, not per command. Reopen discussion for scope changes and every improved candidate's adoption. Preserve pending decisions and the accepted result; neither silence nor a deadline authorizes a choice. Challenge assumptions with evidence, counterexamples and alternatives rather than reflexively agree with the user.
2. Read `../taskflow-brief/SKILL.md`. Give an early brief inside approved discovery scope; distinguish required, optional, examples, preferences and hypotheses. Derive improvement criteria from task guidelines/requirements and ask the user if priorities still conflict. Inspect the actual input and goal/output artifacts before architecture decisions.
3. Establish execution time, budget and host capabilities from observed tools. In COFA or another managed browser IDE, read [startup checks](references/cofa-startup.md) before choosing a mode; distinguish observed, reported, documented-only and unknown support. Read `../taskflow-parallel/SKILL.md` when independent work exists, including its pinned model-routing policy. Select allowed model/effort by difficulty and failure impact; never use Astra, inherit an unknown default or auto-update models/settings. A skill cannot create native agent support. If unavailable, state serial/self-review mode. Never launch extra model CLIs, use personal credentials or change global settings as a workaround.
4. For a prediction, optimization, retrieval or analysis pipeline, read `../taskflow-model/SKILL.md`: specify input/output semantics, minimal necessary modules, method choices/assumptions and evaluation before implementation. For other deliverables, select the smallest complete path appropriate to their actual requirements. Discuss and approve the implementation batch; do not force a mathematical model onto a document or unrelated task.
5. Keep a short task board and requirement-to-check mapping. Assign only approved concrete outcomes, write scopes, shared resources, contract versions and completion checks. Build a complete baseline through real input/output; distinguish execution, validity and quality. Reconcile completion and dispatch newly ready approved work as results arrive. Independent backend modules and a required frontend need not wait for the entire model if their contracts are stable.
6. After the working baseline, read `../taskflow-improve/SKILL.md` when iterative improvement is wanted. Diagnose weaknesses, propose bounded experiments, compare complete results and obtain candidate-adoption approval. After each successful adoption, reassess the new model's actual weaknesses/bottlenecks/failures and propose the next batch. Retain a verified accepted snapshot; unapproved candidates remain separate. Continue only inside approved time/scope and preserve final integration time.
7. **On every new user message while work continues**, run `../taskflow-inbox/SKILL.md` at the next observable boundary. Answer status questions, preserve the objective and process actual decisions/changes. Store unapproved ideas without dispatching them. Never silently drop a request or call an unacknowledged message delivered.
8. Diagnose reproducible failures before speculative changes. Read only the relevant upstream source through `docs/SOURCES.ko.md` in the runtime kit. Use targeted review or simplification when useful, without importing whole upstream processes or overriding this user's approval policy.
9. Read `../taskflow-verify/SKILL.md` before completion. Check the actual accepted combined result and required outputs; reporting a completed experiment is not permission to adopt it. Reserve time for fresh checks and the specified submission.
10. After implementation and checks, read `../understand/SKILL.md`. Apply Understand Anything to the actual final result and deliver a source-grounded Korean explanation of the chosen methods, measured changes, remaining weaknesses and limits. Keep graph-runtime blockers explicit and final source checks current. Then report actual results and any pending user decisions/action.

## Runtime

Project-local installation puts `kit.py`, upstream references and docs in `.taskflow-kit/`. Use `python .taskflow-kit/kit.py --help`; use `python3` if that is the available interpreter. With a source checkout, use its `kit.py` directly. Do not copy private task data to the public pack.

The board is a helper, not a background agent service. While a turn runs, the coordinator must actually use the native dispatch/message/followup tools and reconcile their results. Before yielding with unfinished work, preserve pending requests, active target IDs and blockers; do not imply execution continues after the host stops it.
