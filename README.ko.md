# TaskFlow Kit 1.3.0

처음 보는 과제를 이해하고 작동하는 모델을 만든 뒤, 사용자와 합의한 범위에서 개선안을 비교하는 범용 스킬팩이다. 여기서 **모델**은 AI 모델에 한정되지 않는다. 입력을 받아 목표에 맞는 출력을 만드는 전체 처리 방식과 모듈 구성을 뜻한다. 특정 산업·알고리즘·웹 프레임워크를 정답으로 고정하지 않는다.

## 구성

| 스킬 | 역할 |
|---|---|
| [taskflow-workflow](skills/taskflow-workflow/SKILL.md) | 과제 확인 → 배치 논의·승인 → 최소 모델 → 검증·개선 → 최종 결과 이해 |
| [taskflow-brief](skills/taskflow-brief/SKILL.md) | 원문 근거가 있는 요약과 필수·선택·예시·가정 구분 |
| [taskflow-model](skills/taskflow-model/SKILL.md) | 입력·출력의 의미, 목표·제약·평가 기준과 최소 완성 흐름 정의 |
| [taskflow-parallel](skills/taskflow-parallel/SKILL.md) | 독립 모듈·경쟁 후보 분할, 담당 범위·의존성·공통 자원 조율 |
| [taskflow-inbox](skills/taskflow-inbox/SKILL.md) | 요청 원문 보존, 다음 작업 등록, 실제 메시지 전달 상태 구분 |
| [taskflow-improve](skills/taskflow-improve/SKILL.md) | 현재 채택 모델 보존, 제한된 실험, 공정한 비교·독립 비평과 후보 채택 논의 |
| [taskflow-verify](skills/taskflow-verify/SKILL.md) | 통합·실행·검증 상태 구분과 오래된 검사 근거 거절 |
| [understand](skills/understand/SKILL.md) | 최종 결과물의 구조·동작·선택 이유·검증과 한계를 한국어로 설명 |

TaskFlow 7개와 `understand` 1개, 총 8개를 설치한다. 이 버전은 활성 스킬 수를 유지하면서 COFA 시작 기능 점검, 조건부 데이터·속성 검사, 조건부 로컬 웹앱 검사 참고 지침을 보탠다. 공개 원본과 라이선스를 보존하고 해당 상황에서만 참고한다. [출처](docs/SOURCES.ko.md), [운영 예시](docs/OPERATIONS.ko.md), [검증 범위](docs/VALIDATION.ko.md)를 함께 제공한다.

## 모델을 만들고 개선하는 방식

먼저 원문 요구와 과제 지침에서 무엇이 개선인지 정의한다. 입력·출력의 형식뿐 아니라 의미·단위·오류 처리, 목표·제약·평가 방법을 확인하고 실제 입력부터 출력까지 이어지는 최소 모델을 만든다. 모듈별 방법은 과제 목적과 근거에 따라 선택한다.

현재 채택 모델과 복구 지점을 보존하고 별도 후보에서 실험한다. 방법 교체, 여러 방법의 병렬 비교·혼합, 모듈 추가·삭제·순서 변경이 가능하며 연결 계약과 의존성을 함께 확인한다. 같은 입력·평가 기준과 비교 가능한 실행 조건으로 결과·비용·실패를 비교하고, 독립 비평자는 원문 요구와 실제 결과를 검토한다. 비평자가 배포나 채택을 스스로 승인하지는 않는다.

실행 전에는 **명령마다가 아니라 작업 배치 단위**로 범위·완료 기준·실험 한도·복구 방법을 보고하고 논의한 뒤 명시적 승인을 받는다. 승인 범위의 구현·테스트는 이어서 진행한다. 범위가 바뀌거나 개선 후보를 현재 채택 모델로 채택하려면 다시 논의하고 승인을 받아야 한다. 실험 승인에는 후보 채택 승인이 포함되지 않는다.

사실·사용자 선호·검증 전 가설을 구분한다. 근거 없이 동의하거나 칭찬으로 결론을 대신하지 않고, 증거·반례·대안과 이유 있는 권고를 제시한다. 우선순위 충돌이 해결되지 않으면 사용자에게 확인하며, 임의 가중치로 결정을 만들어내지 않는다. 침묵과 기한 경과는 승인이 아니다.

후보를 승인받아 반영한 뒤 실제 통합 결과를 새로 검사하고, 실패하면 이전에 채택한 모델로 복구한다. 성공할 때마다 승인된 범위에서 새로 채택한 모델의 실패·병목·약점을 진단하고 다음 실험을 제안한다. 승인받지 않은 다음 배치는 시작하지 않는다. 자세한 기준은 [공통 의사결정 정책](skills/taskflow-workflow/references/decision-policy.md)에 모아 둔다.

## 요구 환경과 실행 범위

조율 도구는 Python 3.10 이상과 표준 라이브러리 SQLite를 사용하며 계정·API 키·MCP·추가 패키지 없이 동작한다. Understand Anything 그래프 실행에는 Node.js ≥22, pnpm ≥10과 원본 코어 빌드가 별도로 필요하다. 의존성은 미리 설치하거나 자동 다운로드하지 않는다. [최종 결과물 이해 안내](docs/UNDERSTAND-ANYTHING.ko.md)를 따른다.

프론트엔드·백엔드 모듈이나 경쟁 후보의 실제 병렬 실행에는 **제공 AI 환경의 native 하위 에이전트 도구**가 필요하다. 작업판 등록은 실행이나 전달의 증거가 아니다. 도구가 없으면 순차 모드로 진행하고, 독립 비평을 수행하지 못한 경우 그 한계를 밝힌다.

개선 절차는 스킬 지침과 로컬 기록을 기존 `board`·`check` 명령과 함께 사용하는 방식이다. 자동 실험 실행기, OS 차원의 승인 강제 기능, 상시 감시 서비스는 추가하지 않는다.

대회나 조직에서 개인 스킬·공개 저장소·설치·AI 도구를 허용하는지는 실제 적용 규칙을 확인해야 한다. 공개 소스는 [arcturus0637-rgb/taskflow-kit](https://github.com/arcturus0637-rgb/taskflow-kit)에 제공한다. Git Clone 또는 저장소 ZIP 다운로드로 가져올 수 있다.

## native 에이전트 모델 선택

난이도별 고정 기본값은 basic: Luna 6 / low, standard: Sol 6.1 / medium, critical: Sol 6.1 / high다. 사용자 허용 목록은 Sol 6.1, Terra 5.6, Luna 6, Sol 6.0으로 한정하며 Astra는 어떤 경우에도 허용하지 않는다. Terra 5.6은 보존된 선택지지만 현재 관찰된 호스트에 검증된 native ID가 없어 `null`이다. ID를 추측하거나 Terra 6.1·Sol 5.6으로 대체하지 않는다. Sol 6.0은 명시적으로 허용된 대안이며 버전 자동 대체는 없다.

오프라인 `agent-plan`은 호출자가 실제 native 도구 메타데이터에서 관찰한 정확한 ID와 제안 모델을 대조해 계획을 검증한다. 에이전트를 실행하거나, 매핑·설정·승인을 바꾸거나, 부모 모델을 변경하지 않는다. 실행 전 native 도구가 해당 모델·노력값 선택을 지원하는지 확인하고 정확한 모델과 노력값을 명시해 전달한다. 키트·모델·스킬·upstream·의존성·전역 설정은 자동 갱신하지 않는다. 자세한 내용은 [모델 라우팅 정책](skills/taskflow-parallel/references/model-routing.md)을 참고한다.

## 실제 과제 폴더에 등록

압축을 푼 팩의 `kit.py`를 기준으로 실행한다. PROJECT는 실제 과제 폴더로 바꾼다. 현재 소스 팩 폴더 자체를 대상으로 설치하지 않는다.

```text
python kit.py verify-bundle
python kit.py install --project PROJECT --dry-run
python kit.py install --project PROJECT
```

과제 폴더의 `.agents/skills`에 8개 스킬을, `.taskflow-kit`에 보조 도구와 원본 소스를 배치한다. 기존 `AGENTS.md`와 과제 파일은 수정하지 않는다. **내용이 다른 기존 설치 파일이 있으면 덮어쓰지 않고 중단한다.** 같은 바이트의 재설치는 가능하지만 이 명령은 이전 버전을 조용히 업그레이드하거나 기존 설치를 삭제하지 않는다. 기존 설치를 바꿔야 한다면 차이와 보존·복구 방법을 먼저 검토한다.

설치한 현재 세션이 새 스킬을 바로 발견하는지는 제공 환경에 따라 다르다. 발견하지 못하면 실제 과제 세션에서 `.agents/skills/taskflow-workflow/SKILL.md`를 직접 읽도록 요청하거나 환경의 공식 새 세션 안내를 따른다. Python이 없으면 `skills/taskflow-workflow/SKILL.md`부터 수동 참고할 수 있지만 SQLite 작업판·검사 증거 도구는 사용할 수 없다.

## 시작할 때 붙여 넣을 요청

```text
$taskflow-workflow을 사용해서 이 과제를 진행해줘.
원문 근거로 목표·필수 요구·제출물·제약과 입력·출력의 의미·평가 기준을 정리해줘.
사실, 내 선호, 검증 전 가설을 구분하고, 우선순위 충돌은 나와 논의해줘. 근거·반례·대안을 검토해 권고해줘.
실제 입력부터 출력까지 연결되는 최소 모델과 모듈별 방법을 제안해줘.
범위·완료 기준·실험 한도·복구 방법을 작업 배치로 보고하고 내 명시적 승인 뒤 구현·검사를 진행해줘. 명령마다 승인받을 필요는 없어.
실제 하위 에이전트 도구가 있으면 독립 프론트엔드·백엔드 모듈이나 경쟁 후보를 병렬로 맡겨줘. 수정 범위·공통 계약·의존성을 분리해줘.
진행 중 내 요청은 원문과 ID를 보존해 담당자의 다음 작업으로 등록하고 실제 도구로 전달해줘. 등록·전달 수락·착수·통합·검증을 구분해줘.
현재 채택 모델을 보존하고 별도 후보에서 제한된 실험을 해줘. 같은 기준으로 비교하고 독립 비평자에게 원문 요구와 실제 결과를 검토하게 해줘.
범위 변경과 각 개선 후보의 채택은 다시 논의하고 내 승인을 받아줘. 침묵이나 기한 경과를 승인으로 보지 마.
승인받아 반영한 뒤에는 실제 통합 결과를 검사하고, 승인 범위에서 새 모델의 실패·병목·약점을 진단해 다음 실험을 제안해줘. 승인받지 않은 다음 배치는 시작하지 마.
최종 구현·통합·검증 뒤 $understand를 적용해 구조·데이터 흐름·선택 이유·실제 검증과 한계를 한국어로 설명해줘.
원본 그래프 실행이 불가능하면 이유와 미실행 상태를 밝히고 실제 결과물에 근거한 UNDERSTAND.ko.md를 제공해줘.
```

## 확인 범위와 한계

기존 v1.1의 자동 검사 46개 통과와 깨끗한 프로젝트 설치는 과거 검증 이력이다. v1.3.0의 실행 여부와 확인 범위는 [검증 문서](docs/VALIDATION.ko.md)와 해당 실행 로그를 확인한다. 새 참고 지침이 추가 검사를 실행했다는 뜻은 아니다.

작업 예약은 협력 규약으로, 에이전트의 임의 파일 수정을 OS 차원에서 차단하지 않는다. 같은 파일이 필요한 작업은 기다리거나 독립 사본에서 작업 후 통합해야 한다. 메시지 타임아웃 뒤 원격 전달의 정확히 한 번 처리는 보장할 수 없어 같은 요청 ID로 중복 방지를 한다.

스킬만으로 모든 과제의 정답·대회 점수·최적해·제출 성공을 보장하지 않는다. 원문 라이선스와 적용 범위는 각 upstream 폴더에 유지된다. 팩을 실제로 시험한 결과와 미확인 사항은 VALIDATION 문서에 분리해서 기록한다.
